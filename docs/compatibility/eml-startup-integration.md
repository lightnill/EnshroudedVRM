# EML startup integration feasibility

Read-only investigation, 2026-11-04. No plugin was built, no EML source was copied into this project, and neither game installation was changed by this investigation.

## Result

The clarified target is one shared mod with interchangeable startup adapters: our standalone `dinput8.dll`, or a small original adapter invoked by an existing EML installation. Both use the same VRM runtime, startup policy, settings and models. Copying/replacing EML's bootstrap is not part of the request. Nexus/Vortex delivery is also required, and must be evaluated independently from EML's native hosting capability.

EML 0.2.0 cannot currently replace our startup entry through its native runtime-mod mechanism. It exposes DLL registration plumbing, but the stage that would load those DLLs is commented out. The same runtime-stage implementation remains on the inspected upstream main branch. The user's existing EML installation can coexist with a separate VRM bootstrap; that is different from EML hosting the VRM startup component.

Do not ship an EML manifest or detect an EML-named DLL and then claim native VRM startup is working. The currently proposed standalone input proxy remains necessary unless an actual supported EML build passes the integration gates below. This finding is specific to the inspected version, not a prediction about future EML releases or forks.

## Nexus/Vortex delivery

The author's [Enshrouded Vortex Extension page](https://www.nexusmods.com/site/mods/2453?tab=description) documents EML 0.2.0 setup and native proxy DLL support, including `dinput8.dll`, with adjacent files deployed to the game folder. A Vortex user can therefore have a managed native package and EML in the same installation; this does not require EML itself to load that DLL. This is documented extension behavior, not a tested install of our new package. No extension code was copied, modified or redistributed.

For a Vortex-compatible variant, test the actual installer routing and deployed member layout, conflict handling, update/enable/disable/purge, retained personal state and normal Steam startup. Check the extension's documented omission of README/license files against our integrity manifest and required notice distribution.

Vortex's [deployment documentation](https://github.com/Nexus-Mods/Vortex/wiki/MODDINGWIKI-Users-General-Deployment-Methods) describes hardlink deployment as default. Our current bootstrap and general read-handle admission explicitly reject file link counts other than one (`src/standalone_bootstrap_main.cpp`, `src/standalone_files.cpp`). Standard hardlinked deployment is consequently a concrete compatibility concern to solve and test. Separate immutable verified managed inputs from writable state/log protection; do not remove all hardlink/reparse checks or change user deployment settings as a substitute for support. No admission code has been changed here.

## Inspected public interface and lifecycle

The release reference is `v0.2.0`, commit `16708594d686b030d909f2d835b199d879ea9ad8`. Relevant crate tree IDs on inspected main matched the release; the runtime source was also read directly from main.

- EML discovers `mod.json`; the documented source layout uses `src/mod.lua`. Its manifest model has runtime-related capability names. See the [setup guide](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/docs/src/eml/develop/setup.md) and [manifest contract](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/crates/mod-loader-base/src/registry/manifest.rs).
- The Lua-facing registration interface is `loader.runtime.register_dll(path)` with an advertised `loader.features.runtime.dll` flag. The proxy enables the runtime option, so a capability flag can be present despite the inactive native loading stage. See the [loader API](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/crates/mod-loader-lua/src/env/loader.rs) and [proxy initialization](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/crates/dbghelp-proxy/src/init.rs).
- Registered DLL paths are collected and passed to the runtime stage, but `loader_attach` does not load them. The library-loading loop and retained handles are comments, and the corresponding loading dependency is disabled. A runtime-stage log message alone is not a DLL load. See the [release runtime stage](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/crates/mod-loader-runtime/src/lib.rs) and [inspected main runtime stage](https://github.com/Brabb3l/kfc-parser/blob/main/crates/mod-loader-runtime/src/lib.rs).
- Runtime-only manifests also need care: the inspected Lua runner starts scripts for patch/export capabilities, not runtime capability alone. Do not misdeclare an asset-patching capability merely to force startup. See the [runner](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/crates/mod-loader-lua/src/runner/mod.rs).
- The supplied Lua environment omits OS/package libraries, so there is no supported standard-Lua native-loading escape path to substitute for that missing stage. Do not add shell execution, binary dropping or a replacement Lua runtime as a workaround. See the [Lua environment](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/crates/mod-loader-lua/src/lua/mod.rs).
- The inspected debug proxy invokes its initialization from `DllMain`. Uncommenting a nested native load would not by itself establish a safe startup callback. See the [proxy lifecycle](https://github.com/Brabb3l/kfc-parser/blob/16708594d686b030d909f2d835b199d879ea9ad8/crates/dbghelp-proxy/src/lib.rs#L527) and Microsoft's [DLL best practices](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices).

These observations come from source and interface inspection, not execution of an EML adapter. No claim is made that every possible fork has the same limitations.

## Requirements for a real hosted integration

1. **A usable native startup hook in the actual EML build.** It must execute a runtime-only mod, load its native component exactly once, retain it for its required lifetime and provide a defined failure path. Its initialization callback must be outside the Windows loader lock and early enough to arrange our Vulkan layer before the game's Vulkan instance is created. The inspected API/feature flag alone does not meet this requirement. Upstream native support, or a separately scoped EML change, is needed first.
2. **A small original VRM startup adapter.** Use EML metadata and a minimal registration script for the supported contract, plus our own native layer-setup component. The existing VRM runtime is a Vulkan layer, not a conventional EML plugin entry; loading the runtime DLL alone does not insert it into the game's Vulkan dispatch chain. Keep model parsing, rendering, menu and multiplayer code in the existing runtime.
3. **An explicit package/path contract.** A hosted component would live under `mods/enshrouded-vrm/`, whereas our current bootstrap requires its own module beside the game EXE. Define and validate that extra layout without relaxing executable, package, manifest, path/link or disabled-startup admission checks. Prefer an unpacked adapter with stable relative paths; archived-mod temporary extraction is not assumed compatible. Preserve user models/settings and the core package location.
4. **Reliable selection of one startup route.** Check the selected game's installation and the actual supported loader/version/capability. A DLL basename or stale `eml.json` is insufficient; EML may use a different proxy name. The hosted mode would omit/disable our root input proxy, and the standalone mode would not also register the adapter. If both are accidentally present, prevent duplicate runtime activation and issue a clear diagnostic. Never overwrite, auto-update or silently replace EML to enable the feature.
5. **Independent license/provenance checks.** Write the adapter and script from the public interface contract. Do not copy or link EML implementation/SDK code, ship its loader, or adopt a fork without reviewing the exact selected files and distribution terms. EML's GPL-3.0 source is not a license to include it under our MIT notice. Existing third-party notices remain intact. A possible upstream contribution is separate work; no author contact, contribution or EML modification is authorized by this read-only investigation.
6. **A version-specific functional test.** Verify a native probe callback, VRM-layer discovery, stable F8/avatar, disable/failure behavior, menu/world transitions, repeat startup, input chaining and two-player behavior on both machines. Compare EML alone, standalone VRM with EML, and hosted mode using the same supported game/build. Back up the KFC index/resource files before EML tests because even a previous print-only EML probe rewrote them. Do not equate a Lua print, DLL registration, feature flag or module mapping with working rendering.

## Current practical route

If a verified EML `dbghelp.dll` already exists, leave it in place and test it alongside our original standalone `dinput8.dll` entry. If EML occupies `dinput8.dll`, its preserved input-chain route needs the same explicit rename, export routing and timing checks as other input loaders. Previous launcher-based coexistence results, recorded in [loader-coexistence.md](loader-coexistence.md), do not verify this new normal-Steam entry or EML-hosted startup.

Track the user's two desired entry paths explicitly. EML-hosted startup remains unresolved for inspected 0.2.0 because the host does not execute registered DLLs; Vortex native deployment remains a separate achievable packaging target that needs actual validation. Plan both adapters around the same startup/core artifacts, prove any proposed EML hook before relying on it, and do not substitute coexistence or manager installation for the requested hosted-mode acceptance. Further upstream/fork changes would need their own concrete scope and license review rather than being silently bundled into this mod.

## 0.5.0 implementation follow-up

The investigation above describes the earlier state. The implemented standalone input route subsequently passed actual Vortex install/replace/enable/disable/purge checks and live coexistence with an existing EML 0.2.0 dbghelp.dll installation on game build 26430625. Immutable hash-verified hardlinks are supported while writable-state protections remain. Desktop/laptop multiplayer checks passed. No EML-hosted adapter was added; this release starts independently. See validation/0.5.0 for scope and exact native comparisons.
